# RENTIKA CRM — production-стек

Self-hosted multi-tenant версия CRM: backend на Python/FastAPI, frontend на
React + TypeScript + Vite, база — Postgres с Row Level Security, docker-compose
для развёртывания на своём сервере. Это отдельная ветка развития проекта,
следующая после демо-версии (`index.html`, Artifact) и Supabase-версии
(`index-supabase.html`) — подробности решения по стеку и вся аргументация
выбора Python/React — в `PRODUCTION_ARCHITECTURE.md`.

## Что реализовано

- **Multi-tenant модель**: `Business` (тенант) → `Employee` (сотрудник,
  включая владельца) → `Position` (должность) → `Permission` (право
  должности на ресурс: `none`/`view`/`edit`). Владелец бизнеса всегда имеет
  полный доступ вне зависимости от должности.
- **Двойная изоляция тенантов**: на уровне кода (фильтр `business_id` в
  каждом запросе) И на уровне самой Postgres (Row Level Security — политики
  читают сессионную переменную `app.rls.business_id`, которую выставляет
  backend в начале обработки каждого запроса). Проверено вручную на
  реальном Postgres: без выставленного контекста запрос от прикладной роли
  `rentika_app` не видит ни одной строки, даже если написать `WHERE
  business_id = '...'` явно — RLS отсекает раньше, чем отработает WHERE.
- **Аутентификация**: email/пароль, Argon2id-хэширование, JWT access-токен
  (30 минут, в заголовке — не в cookie, чтобы не участвовать в CSRF) +
  refresh-токен (30 дней, httpOnly-cookie, ротируется при каждом
  использовании, хранится в БД только как SHA-256-хэш).
- **Политика паролей** (NIST SP 800-63B, 2024): минимум 12 символов, без
  принудительных "1 цифра / 1 спецсимвол", проверка по базе утечек Have I
  Been Pwned (k-anonymity — наружу уходят только первые 5 символов SHA1,
  сам пароль никогда не покидает сервер), блокировка на 15 минут после 10
  неверных попыток входа.
- **Двухфакторная аутентификация** — TOTP (RFC 6238), совместима с Google
  Authenticator, Microsoft Authenticator и Яндекс Ключ. Backup-коды на
  случай утери телефона (хранятся как хэши, одноразовые).
- **ACL**: у каждой должности — свой набор прав по ресурсам (оборудование,
  клиенты, аренды, финансы, сотрудники). Управление должностями и ACL-матрицей
  — исключительно у владельца бизнеса (сознательное ограничение против
  привилегированной эскалации — см. комментарии в `backend/app/api/routes/positions.py`).
- **Бизнес-логика проката** перенесена из клиентского прототипа: ступенчатый
  тариф (`app/services/pricing.py`), проверено регрессионным тестом на
  эталонном примере из истории проекта (29-дневная аренда → 1287 ₽ — то же
  число, что в `index-supabase.html`).
- **Security hardening**: security-заголовки на reverse-proxy (Caddy),
  rate limiting (slowapi) на login/register/2FA, аудит-лог действий
  (`audit_log`), непривилегированный пользователь в Docker-образе backend,
  секреты только через переменные окружения.
- **docker-compose.yml**: db (Postgres) / redis / migrate (одноразовый) /
  backend / frontend / reverse-proxy (Caddy, автоматический HTTPS). Наружу
  смотрит только reverse-proxy.

## Что НЕ сделано (сознательно, для следующих итераций)

- Рассылка приглашений сотрудникам по email — временный пароль сейчас владелец
  передаёт лично.
- UI раздела «Финансы» (отчётность по периодам) — на бэкенде есть все данные
  для расчёта, эндпоинт агрегации ещё не написан.
- Восстановление пароля по email.
- Impersonation для техподдержки (Иван «входит как» бизнес-клиент) — если
  понадобится, делать отдельно, с обязательной записью в audit_log.
- Календарь и часть аналитики дашборда из демо-версии — перенесены только
  ключевые сущности (оборудование/клиенты/аренды/сотрудники), не весь UI.

## Как проверялось

Backend — 27 автотестов (`cd backend && pytest`): регистрация/логин/refresh-
ротация/блокировка после перебора, ACL на всех уровнях (владелец/сотрудник
с view/сотрудник с edit/сотрудник без должности/попытка эскалации через
employees:edit), tenant-изоляция (бизнес A не видит и не может изменить
данные бизнеса B даже подобрав UUID), 2FA (setup/confirm/login/backup-коды),
полный сценарий аренды с проверкой суммы. Тесты используют SQLite — быстро,
без внешних зависимостей, но RLS (специфика Postgres) в них физически не
участвует.

Отдельно, вручную, всё то же самое прогнано через живой HTTP-сервер поверх
**настоящего Postgres с включённой RLS** — включая прямую проверку в psql,
что роль `rentika_app` без выставленного `app.rls.business_id` не видит вообще
ничего, что бы ни было в `WHERE`. В процессе этой проверки нашёлся и был
исправлен реальный баг (обработчик `after_begin` в `app/database.py`) —
RLS-контекст изначально не переживал `commit()` внутри одного запроса, из-за
чего `db.refresh()` после сохранения падал под настоящей Postgres (тесты на
SQLite этого не ловят, т.к. RLS там не участвует).

Frontend — тайпчек и продакшн-сборка (`npm run build`) проходят чисто.

`docker compose config` проходит валидацию. Полный `docker compose up` в этой
сессии проверить не удалось — Docker-демон недоступен в текущей песочнице
(это ограничение среды, где собирался проект, не самого проекта) — поэтому
перед реальным продакшн-запуском стоит один раз прогнать `docker compose up
-d --build` на целевом сервере и свериться с чек-листом ниже.

## Быстрый старт

```bash
cp .env.example .env
# отредактируйте .env: пароли, JWT_SECRET, домен, PLATFORM_ADMIN_EMAIL

docker compose up -d --build
```

После первого запуска:

1. Откройте `https://<ваш-домен>/register` и зарегистрируйте первый бизнес.
2. Если хотите получить права платформенного администратора (обзор всех
   бизнесов) — email из `PLATFORM_ADMIN_EMAIL` в `.env` получит их
   автоматически при регистрации; если .env заполнили позже — выставьте
   вручную: `UPDATE users SET is_platform_admin = true WHERE email = '...';`
3. Обновите пароль роли `rentika_app` — миграция создаёт её с временным
   паролем `changeme`: `ALTER ROLE rentika_app PASSWORD '<то, что в
   DATABASE_URL>';` (или отредактируйте `alembic/versions/0001_initial.py`
   до первого запуска, если предпочитаете задать пароль сразу).

## Локальная разработка без Docker

```bash
# backend
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# нужен локальный Postgres — см. DATABASE_URL/DATABASE_ADMIN_URL в .env.example
alembic upgrade head
uvicorn app.main:app --reload

# frontend (в отдельном терминале)
cd frontend
npm install
npm run dev  # http://localhost:5173, /api проксируется на localhost:8000
```

Тесты backend: `cd backend && pytest` (SQLite, ничего дополнительно
поднимать не нужно).
