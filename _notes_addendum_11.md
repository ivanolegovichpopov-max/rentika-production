

## Одиннадцатый проход: новый класс сбоя деплоя (устаревший билд при статусе "live"), 4 доработки по репорту пользователя после ручной проверки (2026-08-28)

Пользователь написал «Проверь деплой» сразу после десятого прохода. Проверка
`raw.githubusercontent.com` (исходники) против `mcp__Render__list_deploys`
показала оба сервиса на нужном коммите со статусом `live` — по всем прежним
критериям деплой выглядел успешным. Пользователь тем не менее прислал
скриншоты живого дашборда с явно старым интерфейсом (старый плейсхолдер
заметок «Новость для сотрудников…», нет чекбокса «выполнено», нет диапазона
дат у переключателя периода).

### Новый, десятый по счёту класс сбоя деплоя: "live", но раздаётся старый бандл

В отличие от всех девяти предыдущих сбоев (автодеплой не срабатывал вообще,
либо миграция падала при сборке backend'а) — на этот раз **сам Render**
показывал корректный коммит и статус `live` на обоих сервисах. Расхождение
нашлось только прямым запросом к самому JS-бандлу через `fetch()` из
консоли реального браузера пользователя (`mcp__claude-in-chrome__javascript_tool`,
`cache: 'no-store'`, поиск маркерных строк вроде нового плейсхолдера
заметок) — WebFetch не годится для этой проверки в принципе (SPA рендерится
JS-ом, WebFetch видит только пустой `#root`, теги `<script>` из markdown-конвертации
вырезаются). Бандл, отданный "live"-деплоем, не содержал ни одного маркера
нового кода — то есть frontend-статик-сайт Render отчитался об успешном
деплое нужного коммита, но реально собрал/отдал артефакт из закешированной
предыдущей сборки.

**Исправлено**: `mcp__Render__trigger_deploy` с `clearCache: true` на frontend
(до этого всегда вызывался без этого флага) — пересборка заняла те же ~12
секунд, но новый бандл (проверен тем же способом через `fetch()` из
консоли) уже содержал все маркеры нового кода. Заодно этим же передеплоем
подхватился ещё один коммит, который пользователь запушил уже ПОСЛЕ
предыдущей проверки (`59551047`, "зд") — на момент `trigger_deploy` он уже
был на `main` веткой `HEAD`.

**Правило на будущее**: `mcp__Render__list_deploys`/`get_deploy` со
статусом `live` на правильном коммите — необходимое, но **не достаточное**
подтверждение, что задеплоенный код актуален (для static site-сервисов,
где нет прямого способа как у backend'а прочитать `/openapi.json` и увидеть
структуру). Финальная проверка frontend-деплоя — прямой `fetch()` JS-бандла
из реального браузера (через Claude in Chrome) с `cache: 'no-store'` и
поиском маркерной строки нового кода, а не только сверка коммитов. Если
маркер не находится при "live"-статусе на правильном коммите — сразу
`trigger_deploy` с `clearCache: true`, без дополнительных вопросов
пользователю.

### Репорт пользователя после ручной проверки на пересобранном деплое: 6 пунктов, 4 доработки + 2 ложных срабатывания

После фикса деплоя пользователь проверил живую версию заново и прислал 6
замечаний. Проверка кода показала: два из шести («логотип не реализован»,
«повторные клиенты не реализованы») оказались **ложными срабатываниями** —
обе функции из десятого прохода на самом деле в коде присутствуют и
работают (карточка «Логотип бизнеса» — на вкладке «Профиль», видна только
владельцу; плашка «Повторные клиенты» — на вкладке «Финансы», в одном ряду
с «Депозиты на удержании»/«Начислено по активным арендам»); подтверждено
прямым переходом по вкладкам в реальном браузере пользователя через
Claude in Chrome со скриншотами. Дело было в том, что обе функции живут не
на самом дашборде, а на отдельных вкладках, которые пользователь при
беглой проверке дашборда не открывал — пользователю объяснено, где именно
искать, без каких-либо правок кода по этим двум пунктам.

Оставшиеся 4 пункта — реальные, все реализованы:

**1. Убран чекбокс «выполнено» на записях доски заметок.** Пользователь
уточнил, что был согласен с моим же более ранним (не зафиксированным явно
в этом документе, из более раннего обсуждения) мнением, что чекбоксы здесь
не нужны — сама функция из п.5 десятого прохода отменена по факту. Убраны:
чекбокс в `DashboardTab.tsx` (`NotesPanel`), функция `toggleDone`,
CSS-классы `.note-done-check`/`.note-item.note-done`. **Сознательно
оставлено нетронутым**: колонка `dashboard_notes.done` и эндпоинт
`PATCH .../notes/{id}` на backend — по себе безвредны (не используются
фронтендом, для отдельного отката потребовалась бы новая миграция и правка
уже покрывающего их теста `test_note_done_toggle`); если это неприемлемо —
сказать явно, уберу отдельным заходом.

**2. Кнопка «Выйти» перестала быть прибита к низу сайдбара.** По итогам
десятого прохода `sidebar-spacer` был перемещён ПОСЛЕ блока «Команда»,
чтобы прижимать к низу только кнопку выхода (обычная конвенция — выход
отдельно от навигации) — пользователь посчитал, что и это лишнее при
коротком списке разделов. `sidebar-spacer` убран полностью (div и обе CSS-
декларации, включая версию для узкой раскладки) — «Выйти» теперь идёт
сразу за списком команды тем же потоком, без принудительного пустого места
на высоких экранах.

**3. «Новая аренда» больше не переключает вид.** Раньше кнопка в топбаре
(`Dashboard.tsx`) вызывала `navigate("rentals", {..., openCreateRental: true})` —
всегда переключала на вкладку «Аренды», прежде чем открыть форму. Я
согласился с предложением пользователя оставаться на дашборде: `RentalsTab.tsx`
уже содержал полностью самостоятельный `CreateRentalModal` (свои
`clients`/`equipment`/`rentals`/`onCreated` через `useData()`) — экспортирован
и поднят на уровень `DashboardShell` (`Dashboard.tsx`), где `useData()` и
так уже вызывается (тот же приём, что уже применялся для карточек
клиента/оборудования с дашборда в шестом проходе — рендер поверх оболочки,
без `setView`). Кнопка теперь просто открывает булево состояние
`showCreateRental`, без навигации; своя собственная кнопка «+ Новая аренда»
внутри вкладки «Аренды» продолжает работать локальной копией той же
модалки независимо. Сигнальный счётчик `createRentalSignal`/проп
`openCreateSignal` из десятого прохода убран как более не нужный.

**4. Финансовые стат-плашки выделены цветом.** Я согласился с
наблюдением пользователя — плашки уже отличались моно-шрифтом цифр
(`mono`), но не цветом. У `StatTile` (`DashboardTab.tsx`) новый проп
`money` (стоит у тех же 4 плашек, что уже используют `mono`: «Выручка»,
«Депозиты на удержании», «Компенсации», «Ожидаемая выручка») — левая
цветная полоса и цвет значения через уже существующий токен `--good`
(тот же зелёный, что и у положительной дельты `.stat-delta.good`), новый
токен заводить не потребовалось.

**Итоговая проверка**: backend не менялся в этом проходе — `pytest`
по-прежнему 74/74 (перепрогнан для подтверждения отсутствия регрессии).
Frontend: `npx tsc --noEmit` — чисто; `npx vite build` — успешно
(60 модулей). Обновлённый архив `rentika-production.zip` передан
пользователю — требуется его действие: занести изменения в GitHub-
репозиторий тем же способом, что и раньше, затем проверить деплой по уже
устоявшейся методике, **дополненной в этом проходе прямой проверкой
бандла через `fetch()` из браузера** (см. выше).
